# RIC-132: explicitly approved internal task

The first action is `task.create`, contract version 1. From a supported cited answer, the owner writes the exact task title and optional calendar due date, then prepares an immutable proposal. Preparing does not create a task. The task approval section displays server-normalized values, no client link, visibility to practice members, and ten-minute expiry. Only **Approve and create task** executes it. Rejection has no task effect. This slice does not let the model generate arbitrary tool calls or execute anything: the AI contribution remains the cited evidence, while the owner supplies and approves the task wording. No new provider calls, messages, emails, payments, refunds or external effects.

`actionProposals` is one additive table with a tenant/request-key index. It binds tenant, actor identity, allowlisted action/version, exact task payload, all selected evidence versions/hash/spans, each source's approval revision, expiry and an immutable creation receipt. Reusing the preparation key with different input is rejected; retrying the original preparation returns its existing proposal even if it has since expired. There is no proposal-edit API: changed wording/evidence needs a new proposal and approval.

Preparation validates current owner membership and source eligibility through the accepted cited-answer resolver. Approval reads membership, actor, tenant, source approval/revisions and expiry inside the same Convex mutation that creates the task and stores the execution receipt. Database OCC revalidates concurrent membership/source/proposal changes. Revoking then reapproving even the same source version invalidates a pending proposal's bound approval revision. Approval versus rejection has one terminal winner.

Execution shares task validation and insertion through `createTask`. Public `tasks:create` reserves the `proposal:` request-key namespace for the internal approval path; ordinary task receipt behavior remains intact. Approval rejects any pre-existing task under its server-derived proposal key instead of adopting it, including legacy collisions. Concurrent approvals create one task atomically with the proposal receipt. A successful original execution receipt is returned before mutable expiry/source/task-lifecycle checks, after current owner/actor/tenant authorization. Removing the resulting task does not let a retry recreate it. Revoked owners cannot approve or recover private receipts.

The browser remembers only a nonsecret proposal ID under an origin- and tenant-scoped local-storage key. Reload reopens the server-owned proposal/receipt; no task payload, source text or credentials are stored by this feature. Cross-account reuse of the ID is denied by the server. The owner may dismiss the review UI without modifying the durable proposal. Unexecuted dismissed proposals expire. The UI disables expired/stale approvals, but server checks remain authoritative.

Database impact: additive `actionProposals` and one index; no migration/backfill/seed or existing-record changes. Existing knowledge/payment tables and focused integration slices remain unchanged. The `approved-actions` native slice uses a disposable test-only fixture for expiry and role changes; that fixture is never part of deployed backend source. No production deployment is authorized by implementation or local verification.

Focused verification: UI preparation/retry/explicit decision/stale display tests; native same-key preparation, owner/tenant denial, concurrent approval, rejection, expiry, source revoke/reapproval, receipt retry after task removal, approve/reject race, and revoked-owner denial. Existing cited-answer/source-editor UI regressions are retained. Hosted acceptance is a separate gate: prepare/reload exact proposal, approve once, reload one created task/receipt, plus a rejected proposal with no effect in the preserved synthetic practice.

RIC-133 adds the separately documented [existing-task completion action](APPROVED-TASK-COMPLETION.md), using the same explicit decision and receipt lifecycle.
