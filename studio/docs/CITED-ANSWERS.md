# RIC-131: owner-selected cited answers

This initial slice searches up to five explicitly selected, active, currently approved owner-only sources in Precision `/app/knowledge`. It returns at most eight lexical passages of 600 UTF-16 code units each from source versions bounded to 32 KiB. Questions are bounded to 400 characters. No embeddings, ingestion, tools, actions, external search, or clinical/client records are used. Lexical matching requires shared words; it can miss synonyms or support outside the selected passages. Passage search is not an answer-quality claim.

The provider selects up to four exact excerpts that answer the question, or abstains for insufficient, ambiguous or contradictory evidence. Public output contains server-resolved exact quotations rather than free-form generated claims. Citation identity is source ID, immutable version ID, content hash, and half-open UTF-16 `[start,end)` span. Quotes render as text, never HTML or instructions. Model output can only select valid passage indices: extra prose, invalid indices, duplicates, malformed/refused/incomplete output fail closed. Prompt injection is treated as untrusted data; the request offers no tools or executable channel. Model relevance/conflict judgment remains fallible and must be measured, not treated as proof of semantic correctness.

Every search, availability, citation query, and action requires current tenant-owner membership. Every selected source must have `approvedVersionId === currentVersionId`, remain active and owner-only, and point to a version belonging to the same tenant/source. A stale selected source fails the entire request rather than silently changing the selection. After the provider await, a separate internal query rechecks membership and every selected version before returning an answer. The UI then resolves all citations through a reactive server query, so changed, archived, revoked or inaccessible sources remove the displayed result; opening the expandable citation uses that same live query. No answer text from the asynchronous provider result is trusted or cached for display. Changing the question or selection invalidates any in-flight result.

No database schema change, mutation, migration or seed is introduced. Results are transient; source mutations retain their existing revision/approval contract. Generated API adds citedAnswers and pure helpers; the integration harness adds a distinct `cited-answers` slice while preserving source-library and the default full suite. Union payment additions when integrating; never replace them.

## Provider activation and limits

The endpoint is fixed to `https://api.openai.com/v1/responses`; arbitrary endpoints are not accepted. Server environment names are `OPENAI_API_KEY`, `STUDIO_ANSWERS_MODEL`, `STUDIO_ANSWERS_PROVIDER_APPROVED=openai`, `STUDIO_ANSWERS_ENABLED=true`, and `STUDIO_ANSWERS_TENANT_ID`. All are required. The final field restricts execution to the authorized synthetic acceptance practice; other tenants retain local passage search and cannot call the provider through this action. Missing configuration fails closed. Secrets must not be committed or returned in queries/errors.

Initial observed model: `gpt-5-mini-2025-08-07`, using minimal reasoning, at most 600 output tokens, a 20-second timeout, `store:false`, and a strict JSON schema. No retries, response chaining, background mode or tools. Input includes only the question and bounded retrieved excerpts; source IDs and other metadata are omitted. `store:false` does not itself establish zero retention or a general approval to process real practice data. This staging authorization covers a tiny synthetic corpus only. No production activation. Broader rollout needs separately approved data handling, model/billing configuration and spend/rate controls; the current action bounds each call but does not implement a durable account-wide monetary cap.

Availability was observed with an HTTP200 synthetic request, not inferred from the key or a Codex subscription. Three further synthetic cases tested supported evidence, conflicting evidence, and a source injection; all selected the expected answer/abstention. Provider receipts record model, usage, latency and estimated token cost. Public UI displays model/token/latency usage. Monetary estimates in receipts use published standard input/output rates, treating all input as uncached, and are estimates rather than invoices.

Official references: [GPT-5 Mini model, structured output support and pricing](https://developers.openai.com/api/docs/models/gpt-5-mini), [Structured Outputs](https://developers.openai.com/api/docs/guides/structured-outputs). Live availability is recorded separately from documentation.

## Focused verification

- `cd studio && npx vitest run tests/unit/cited-answers.test.tsx`
- `cd studio/backend && STUDIO_INTEGRATION_SLICE=cited-answers node scripts/integration.mjs`
- Frontend/backend TypeScript and one production build.

Unit fixtures cover exact Unicode spans, bounded matching, absent questions, preserved contradictory evidence, invalid citations/prose, provider enablement, request injection isolation/refusal, owner-only mounting and display revalidation. Native local Convex checks cover approved selection, tenant/viewer/anonymous denials, provider default OFF, span/hash tampering, stale/reapproved versions, revocation and archive. Synthetic live provider cases complement these tests; they do not imply universal resistance to malicious sources or clinical answer quality. Hosted staging acceptance remains separate.
