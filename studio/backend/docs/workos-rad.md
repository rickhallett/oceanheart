# WorkOS practice and task slice

This additive schema introduces `tasks` and optional practice creation receipt fields (`createdBy`, `requestKey`) with indexes. Existing tenant, membership and booking records remain valid. No migration, fixture import, external provider write or hosted deployment is performed by the tests.

## Hosted configuration

Set all six Convex environment variables explicitly: `STUDIO_AUTH_MODE=workos`, `WORKOS_CLIENT_ID=client_YOUR_STAGING_CLIENT_ID`, and empty values for `CLERK_JWT_ISSUER_DOMAIN`, `STUDIO_AUTH_ISSUER`, `STUDIO_AUTH_JWKS`, `STUDIO_AUTH_AUDIENCE`. The frontend uses the same WorkOS client ID and separately owns its API key, cookie secret, redirect URI and Convex URL. Never put the API key or cookie secret in Convex auth config or public environment variables.

The providers follow the [official Convex AuthKit configuration](https://docs.convex.dev/auth/authkit/): client-specific HTTPS JWKS and RS256, with `https://api.workos.com/` plus client audience, and the client-scoped user-management issuer without an audience. Custom WorkOS authentication domains are not supported by this bounded configuration. Confirm the actual staging token's issuer is supported before claiming hosted readiness. [WorkOS sessions](https://workos.com/docs/authkit/sessions) documents the user ID in `sub`; Convex's verified `tokenIdentifier` is the membership key. WorkOS `org_id`, role and permission claims do not grant application membership. Issuer changes require reviewed identity mapping, not automatic account merging.

## Commands

- `tenants.list({})`: authenticated membership-derived `{_id,name,role}[]`.
- `tenants.create({name,requestKey?})`: trimmed name 1–100 characters; optional unpadded nonempty request key at most 128 characters. Live clients should always provide a stable UUID per creation intent and retain it on transport retry. Same creator/key/name returns the existing practice; changed name fails `IDEMPOTENCY_MISMATCH`. Omitted keys preserve the existing explicit create contract.
- `tasks.list({tenantId,filter?})`: owner/viewer read, newest first; `filter` is optional for compatibility and accepts `all` (default), `open` or `completed`. Each server-filtered active list returns `{items:[{_id,title,completed,createdAt,revision}],hasMore,limit:200}`. More than 200 active tasks is explicitly signalled; cursor pagination is outside this slice. Tombstones are constrained in the `tenantId,removedAt` and `tenantId,removedAt,completed` index ranges, so removed rows cannot exhaust a list scan. No creator identity or request keys are projected.
- `tasks.create({tenantId,title,requestKey})`: owner only; trimmed single-line title 1–200 characters with no control characters; unpadded nonempty key at most 128 characters. Same tenant/key/creator/title returns the existing task even after completion; changed payload fails `IDEMPOTENCY_MISMATCH`.
- `tasks.setCompleted({tenantId,taskId,completed,expectedRevision?})`: owner only, checks the task belongs to the selected tenant and advances the revision. New clients send `expectedRevision`, so stale divergent changes fail `REVISION_CONFLICT`; same-state retries succeed. The optional field preserves the deployed legacy command signature. A legacy caller without it remains last-write-wins, but still advances the revision for revision-aware clients.
- `tasks.update({tenantId,taskId,title,expectedRevision})` returns `{taskId,revision}` with the actual current revision, including an unchanged normalized title retry; `tasks.remove({tenantId,taskId,expectedRevision})` returns the task ID. Both are owner-only and revision-aware. Removal is a `removedAt` tombstone, not a destructive delete. A private immutable `creationTitle` records the original normalized create title (captured for revision-zero legacy rows at their first edit/removal), so the original create request returns its original ID after a rename or removal and cannot resurrect a task.
- `tasks.today({tenantId,refreshKey})`: owner/viewer read. The backend ignores the refresh key as authority and derives the current `YYYY-MM-DD` plus `[from,to)` from server time and the tenant's stored IANA zone. It returns explicit `setup_required`/`invalid_time_zone` states or a bounded ready result. Active tasks are selected by tenant, absent tombstone and exact due date before the 201-row take, so newer tasks on other dates cannot crowd them out. Owner client links resolve only same-tenant records; every link field remains redacted for viewers.

All protected task commands reread membership. A tenant selector never authorizes access. A viewer is a staff reader, not a patient. Tasks are general practice operations: do not enter clinical notes in titles.

## Safe deployment transition

An old deployed auth-policy version cannot understand `workos`; setting that mode before deploying compatible code correctly rejects configuration. First add `WORKOS_CLIENT_ID` with an empty value while retaining the old selected provider and its existing values. Deploy this reviewed code, which supports both the old provider and WorkOS. Then prepare a private environment file containing all six values for WorkOS and apply it atomically with `convex env set --from-file <private-file> --force` against the explicitly selected staging deployment. WorkOS mode must be paired with its client ID and four empty legacy provider values in the same update. Never print that file or rely on sequential provider changes that temporarily mix incompatible settings. Confirm deployed authentication config and affected hosted requests afterward. Production is outside this authorization.

## RIC-104 / RIC-105: services and contact creation

Additive tables `services` and `clients` each have tenant and tenant/request-key indexes. There is no migration, seed import, booking linkage, editing, publication or archive operation.

`services.create({tenantId,name,durationMinutes,priceMinor,currency:"GBP",description?,requestKey})` returns the service ID. Only owners create; current members read. Names are trimmed, 1–100 characters and reject control characters. Duration is an integer 1–1440 minutes. Price is an integer 0–100000000 minor units (GBP pence). Optional description is trimmed and at most 2000 characters. New services have `active:true`; this field does not establish website publication or booking availability.

`clients.create({tenantId,name,email?,phone?,requestKey})` returns the contact ID. **Only owners may read or create client contacts.** Names follow the same validation. Optional email is trimmed, at most 254 characters with basic syntax validation; optional phone is trimmed and at most 40 characters. Contact fields reject control characters. Blank optional fields are omitted. Email case is preserved; no identity or uniqueness is inferred from contact email. No notes, history, status or clinical data fields exist in this increment.

Both `list({tenantId,paginationOpts:{numItems,cursor}})` commands use native Convex pagination. Request 1–50 items with null initial cursor; results contain `page`, `isDone`, `continueCursor` and Convex pagination metadata. Order is newest first. Services expose only ID, name, duration, price, currency, optional description, active and creation time. Clients expose only ID, name, optional contact fields and creation time. Neither exposes creator identities or retry keys. Reset pagination when selecting another practice. Public/client-facing APIs are not implemented.

Creation request keys are nonempty unpadded strings at most 128 characters. Identical normalized payload and creator with the same tenant/key returns the original ID; changed normalized payload fails `IDEMPOTENCY_MISMATCH`. All commands recheck membership. Fields deliberately remain separate from browser demo models and future booking snapshots.

Local integration now invokes shared `scripts/catalog-checks.mjs` against the native backend: unauthenticated and cross-tenant reads/writes, owner-only contact privacy, viewer service reads, viewer write denial, revocation, six concurrent retries per table, normalized payload idempotency, validation, projections, fresh-client persistence and cursor traversal. Existing booking and auth checks remain included.

For root-operated hosted acceptance, set the same explicit staging environment gates as above plus `STUDIO_EXISTING_CREDENTIALS` to the private existing fixture's absolute path, then run `node scripts/hosted-catalog-acceptance.mjs`. It requires existing synthetic owner/outsider/viewer accounts and existing distinct owner practices. It never creates WorkOS users or practices, does not persist session tokens or duplicate passwords, and makes no provider settings changes. Password grants authenticate the recorded user IDs; real JWKS verification precedes the same catalogue checks. A new private report directory records each created service/contact ID and tenant for exact cleanup. Fixture failures/challenges stop without retry. The original broad acceptance runner remains available separately; it is not the next-slice runner.

## Record management increment

This extends the create/list increment above without deleting records or changing bookings/tasks. Services add `update({tenantId,serviceId,name,durationMinutes,priceMinor,currency,description?,expectedRevision})` and `setArchived({tenantId,serviceId,archived,expectedRevision})`. Clients add equivalent commands with `clientId` and contact fields. Both return the unchanged record ID. All writes require owner membership. `services.list` remains member-readable; every client operation is owner-only.

List projections add `revision` (legacy absent values mean zero). Clients also expose `archived`. Lists accept `archived?:boolean` (default false). Services map archive state onto existing `active`; clients use additive optional `archived`. Active and archived list queries use matching tenant/state indexes. Update commands replace the complete editable field set using the same normalized validation as create; omitted optional fields clear their previous values. No public projection, booking linkage, or provider changes are added.

The retry rule is intentionally small: when current normalized editable fields (or archive state) already equal the command's desired state, return success without a write. Otherwise `expectedRevision` must equal the current revision; apply and increment atomically, or return `REVISION_CONFLICT`. Clients reload on conflict rather than silently overwriting. No edit request key or command-receipt table is needed. Creation retains its existing request key; a private original `creationPayload` preserves the creation fingerprint across later edits and is never projected to clients. Legacy records capture this original fingerprint before their first edit.

Duplicate contacts, including shared family email addresses, are permitted. Creation keys prevent accidental retry duplicates; names and email addresses are not uniqueness keys and no automatic merge occurs. Future bookings must snapshot service name/duration/price/currency when booked. Existing bookings contain no service ID and are not retrofitted.

`clients.list` additionally accepts `search?:string`, trimmed to at most 100 characters / 16 whitespace-separated terms. It uses a normalized name/email text index with tenant and archive equality filters inside the index query. Results are relevance ordered with native pagination; empty search uses newest-first listing. This is token/prefix search, not arbitrary substring matching or email identity lookup. [Convex text-search semantics](https://docs.convex.dev/search/text-search) includes punctuation tokenization, a 32-character indexed term limit and prefix matching on the final term. Reset the cursor on search/tenant/archive changes.

### Required existing-client backfill

Deploy reviewed additive fields/indexes and functions first, then run the internal `migrations:backfillClientSearch` function against the explicitly reviewed target with `{ "cursor": null }`. It scans at most 100 clients in creation order and patches only missing/default archive state and normalized search text, retaining IDs, contact fields, creator metadata and creation times. It returns `scanned`, `updated`, `isDone`, `continueCursor`. Continue with each returned cursor until `isDone`; record cumulative counts. A repeat run is safe. The mutation is internal, never scheduler-triggered, and does not accept an identity override.

Example operator command, with a private environment file bound to the intended deployment:

```sh
npx convex run --env-file <private-target-file> migrations:backfillClientSearch '{"cursor":null}'
```

Existing rows without `archived` are absent from the new state index until backfilled; rows without search text cannot be found by text search. Therefore client listing/search is **not ready for hosted acceptance until backfill completes and existing IDs/contact fields are checked**. Root performs and records this reviewed step; neither the implementation worker nor the hosted acceptance runner runs migrations or imports against staging. The local integration import is synthetic, append-only and explicitly bound to its isolated localhost backend via its private self-hosted environment file.

Native verification covers same-state retry, stale-version rejection, concurrent divergent edits (one succeeds), archive/restore with stable IDs, owner permissions and revocation, search tenant/archive isolation, duplicate contacts, and a 101-legacy-row backfill crossing the 100-row batch boundary. Hosted acceptance extends the existing-account catalogue runner with these public record-management checks and exact created-record manifests; it performs no WorkOS account creation or migration.

Before hosted catalogue checks change viewer membership, the runner durably records `viewerMembershipBefore` (selected tenant ID, synthetic user ID, prior presence and role) and a cleanup instruction in its private report. An existing owner role or failed checkpoint write stops the run. The checks leave viewer membership absent; if the checkpoint recorded a prior viewer membership, root restores that exact membership during fixture cleanup. No automatic permission restoration is inferred from an incomplete run.

## Manual booking workflow

One practice has one calendar lane. This is owner-operated booking, not a public availability system. Saved weekly hours can be enforced for owner writes through an explicit tenant opt-in that defaults off; buffers, exceptions, external calendar sync, notifications, payments and public booking remain outside this increment.

Owners explicitly save `tenants.setTimeZone({tenantId,timeZone,expectedTimeZone})`; `expectedTimeZone` is the last value or null. An identical value is retry-safe; divergent stale changes fail `REVISION_CONFLICT`. The named time zone is validated by the backend runtime; fixed numeric offsets are rejected. `Europe/London` may be suggested by the UI but is never selected from the browser or saved automatically. `tenants.list` includes the saved optional `timeZone`.

- `bookings.createLinked({tenantId,clientId,serviceId,startsAt,requestKey})` validates owner membership and active tenant-local references, derives end time from service duration, and captures immutable `{name,durationMinutes,priceMinor,currency}` service terms, client label and the saved practice time zone. It fails `TIME_ZONE_REQUIRED` until setup is explicit. The request key and original linked creation payload preserve retry identity even after rescheduling, cancellation or referenced-record edits/archive. New bookings use server-owned lane key `practice`; it is not an authorization input.
- `bookings.reschedule({tenantId,bookingId,startsAt,expectedRevision})` moves a linked booking while preserving its ID, snapshot duration, original booked-at time zone, client and service. Same desired time is a no-op retry; stale divergent changes fail. Cancelled bookings cannot be moved. Legacy unlinked records return `LEGACY_BOOKING` rather than inventing a service snapshot.
- `bookings.cancel({tenantId,bookingId,expectedRevision})` marks a linked or legacy booking cancelled without deletion, retaining terms and identity. Repeated cancellation is a no-op; stale first cancellation fails. Cancellation releases its interval.

`settings.update` accepts optional `enforceBookingHours`; current clients send it explicitly while omitted values from older callers preserve the stored flag. Enabling requires a saved tenant time zone. When enabled, `bookings.createLinked`, compatibility `bookings.create`, `bookings.reschedule` and enquiry booking creation read the tenant row inside the same mutation and require the entire half-open elapsed interval to fit one continuous saved weekday segment. Exact close is allowed; closed days and midnight crossings are not. Repeated-hour boundaries apply to every real occurrence, but a booking cannot bridge a disallowed fold segment. A nonexistent opening or closing makes that local day unavailable. Existing bookings are not rewritten.

Linked and legacy create receipt lookups, same-time reschedule retries and `enquiryConversions` receipts remain ahead of mutable hours checks. An exact retry therefore returns its original ID/result after hours or time-zone changes; a genuinely new write uses current settings. A failed enquiry conversion rolls back any client, link, event and receipt created in that mutation. Hours failures use `OUTSIDE_PRACTICE_HOURS`; missing or malformed enforced zones continue to fail closed with `TIME_ZONE_REQUIRED` or `INVALID_TIME_ZONE`.

All times are safe-integer UTC milliseconds within the supported Date range, intervals are positive and at most 24 hours, and duration is elapsed time. The UI resolves local input using the saved practice zone, rejects daylight-saving gaps, and requires an explicit earlier/later choice for repeated local times before submitting an exact instant. The backend does not infer wall-clock intent from UTC. The agenda displays instants in the current practice zone; original booking time-zone snapshots remain available if setup changes. [Temporal time-zone ambiguity](https://tc39.es/proposal-temporal/docs/timezone.html).

Every creation route, including retained legacy `bookings.create`, and every reschedule shares a transactional tenant/start-time overlap check across all practitioner keys. Non-cancelled legacy records continue to reserve time; missing legacy status means scheduled. Half-open adjacent intervals are allowed, cancellation is excluded, and rescheduling excludes its own record. Existing historical collisions are not rewritten or deleted. The optional practitioner filter on listing remains compatibility-only and cannot bypass collision checks.

`bookings.list({tenantId,from,to,practitionerId?})` is now owner-only and projects only ID, instants, client label/optional IDs, optional snapshot/time zone, status, revision and `legacy`. It never returns creation identity, request key or fingerprint. It includes intervals overlapping `[from,to)` (maximum 31 days) and returns `{items,hasMore,limit:200}`. The indexed lower bound is `from - 24 hours`, followed by `endsAt > from`, so overnight sessions remain visible on the following day until their exclusive end instant.

`bookings.today({tenantId,refreshKey})` is owner-only and derives the same
practice-local window from the stored zone and server time. It includes only
scheduled or legacy-unspecified bookings overlapping `[from,to)`, excludes
cancelled rows, and returns the authoritative date/zone/window plus
`{items,hasMore,limit:200}`. The caller cannot supply bounds. Viewers use only
`tasks.today` and never invoke this owner-contact projection.

Before the ready result, an unset tenant zone returns only
`{status:"setup_required"}`; a saved zone that cannot be resolved returns only
`{status:"invalid_time_zone"}`. These non-ready variants intentionally omit the
ready date, zone, window, refresh delay, items and pagination fields.

`bookings.history({tenantId,bookingId})` is owner-only and returns newest-first `{items,hasMore,limit:200}` transitions with action, timestamp, revision, resulting instants and previous instants on reschedule. The additive `bookingEvents` table captures the authenticated actor internally with every successful create/reschedule/cancel transaction; no-op retries add no duplicate events. There is no public history mutation or deletion. Existing legacy records have only transitions recorded from this version onward, not fabricated earlier history.

The Today database change is one additive task index on
`tenantId,removedAt,dueDate`; existing rows need no backfill and no stored record
is rewritten. The earlier booking changes remain additive optional booking
fields, an optional tenant time zone, an optional tenant enforcement flag, a
tenant/start index and the events table.
No import, hosted deployment or historical-record mutation is required by this
code change. Preserve the existing client-search backfill readiness requirement
from the prior increment. Native acceptance covers snapshot persistence,
linked/legacy collision interoperability, owner-only contacts and history,
archived/foreign references, concurrent identical/different creates,
concurrent divergent reschedules, cancellation and original-create retries,
Today boundaries/caps/redaction, whole-interval weekly-hours enforcement,
conversion rollback, receipt replay after settings changes, and audit
transition order.

Standalone root-operated hosted booking acceptance is `node scripts/hosted-booking-acceptance.mjs`, with the existing explicit staging gates/private credentials path and `STUDIO_BOOKING_TEST_START_MS` set to an exact future UTC millisecond instant. It authenticates existing synthetic users, creates two isolated practice fixtures with recorded request keys/IDs, and runs only the new booking workflow checks. It records prior fixture time-zone/membership state before changing those fields; existing practices are not modified. New fixture records/time zones are intentionally retained for inspection, with no claim that unset time zones can be restored by the current setter. There is no account creation, catalogue-management regression loop, import, migration, reset or automatic deletion. Tokens remain memory-only and the private report contains exact created record IDs.

## Manual enquiries, unsent drafts and deliberate conversion

This owner-only increment captures enquiries entered by the operator. There is no mailbox connection, public capture endpoint, external receipt/send operation or “sent/replied” state. Additive tables hold enquiries, append-only enquiry events and private conversion receipts; no existing data migration is required.

`enquiries.create({tenantId,name,email?,phone?,subject,message,requestKey})` captures an immutable original message/contact snapshot and returns its ID. Contact validation reuses the client rules; subject is a single line of 1–150 characters; message is trimmed 1–5000 characters. Creation retries preserve ID; changed normalized payload with the same key fails. `list({tenantId,resolved?,paginationOpts})` defaults to open records and returns newest-first pages of at most 50 summaries containing name/subject, draft presence, resolution, revision, creation time and optional linked IDs. Contact details, message/draft, creator and fingerprints are excluded. `get({tenantId,enquiryId})` adds protected contact fields, original message and current draft.

`saveDraft({tenantId,enquiryId,text,expectedRevision})` saves trimmed 0–5000-character text (blank clears it). `setResolved({tenantId,enquiryId,resolved,expectedRevision})` explicitly resolves or reopens. Same desired state is retry-safe; stale divergent edits fail `REVISION_CONFLICT`. Saving a draft never sends it or resolves the enquiry. `history({tenantId,enquiryId,paginationOpts})` exposes bounded owner-only capture/draft/conversion/resolution transitions; draft events preserve saved text, including clears. Actor identity is stored internally and not projected.

`convert({tenantId,enquiryId,expectedRevision,requestKey,client,booking?})` takes deliberate choices: client is `{existingId}` or `{create:{name,email?,phone?}}`; optional booking is `{existingId}` or `{create:{serviceId,startsAt}}`. It returns `{clientId,bookingId?}` without resolving the enquiry. Established links cannot change; a booking may be added later to the same client, and omitting booking preserves any existing link. Client email is not an identity/uniqueness key; shared addresses are permitted and no automatic merge occurs. An existing booking must be non-cancelled, tenant-local and linked to the chosen client; legacy unlinked bookings cannot be assigned by guessing.

Conversion invokes extracted `lib/createClient` and `lib/bookingCommands` implementations inside the same Convex mutation as linkage, event and receipt creation. A booking conflict or other error rolls back every write, including a newly created client. There is no second reservation algorithm. A private tenant/request receipt binds normalized deliberate choices, enquiry and authenticated actor to result IDs. Same-key retries return the original result after permission checks, even if the enquiry revision later changes; changed choices fail `IDEMPOTENCY_MISMATCH`. Expected revision is concurrency control, not part of the intent fingerprint. Different simultaneous conversion intents cannot overwrite established links or create a second linked result.

Native checks verify owner/cross-tenant/revocation boundaries, list/detail separation, persisted unsent draft/history and clearing, resolution/reopen, pagination, validation, stale/draft races, same-key and distinct-key conversion races, changed same-key payload rejection, wrong-client booking rejection, rollback of new client/link on overlap, and later linking of a booking to an established client.

Root-operated hosted acceptance is `node scripts/hosted-enquiry-acceptance.mjs`, using the existing explicit staging gates/private synthetic credentials plus `STUDIO_ENQUIRY_TEST_START_MS` (future UTC milliseconds). It creates isolated practice fixtures under existing synthetic accounts, records IDs and prior fixture state, and runs only enquiry checks. It creates no provider accounts, sends nothing, performs no import/reset/migration and stores no session tokens. New fixtures remain labelled and retained for inspection; cleanup requires separate review of exact recorded IDs.

Protected enquiry detail also returns fresh `linkedClient` (ID, name, archive state) and `linkedBooking` (ID, instants, status, optional booked time zone and service name) so the operator can verify the actual linked records. The query independently checks both tenant IDs and the booking's client linkage before projecting them; invalid references fail `LINK_CONFLICT`. No notes, booking creator or private retry metadata is returned. Native checks compare both newly created and deliberately existing linked summaries.

## Gmail: owner-selected import (RIC-125)

This increment connects one Gmail mailbox to a practice and lets its owner page through Inbox metadata, preview a selected plain-text message, and explicitly import it as an enquiry. It does not send mail, modify messages, fetch attachments, synchronise an inbox, or receive push notifications. Client/booking conversion remains the existing deliberate enquiry workflow. Messages without inline plain text cannot be imported; the preview marks attachments and body excerpts truncated to 5,000 characters. The protected enquiry detail records Gmail mailbox/message provenance and whether the imported text was truncated. Deduplication is per practice, mailbox and Gmail message ID, including concurrent requests and reconnects; different practices remain independent.

Convex alone needs `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`, `GOOGLE_REDIRECT_URI`, `GMAIL_TOKEN_ENCRYPTION_KEY` and `GMAIL_ROUTE_SIGNING_KEY`. The latter two are distinct base64-encoded 32-byte random keys. Vercel's matching environment needs only the route signing key, alongside its existing WorkOS session configuration. Keep these in the provider environment stores, never tracked files or browser bundles. The registered staging redirect is `https://oceanheart-studio-env-staging-rick-halletts-projects.vercel.app/practice/integrations/gmail/callback`. Google endpoints are fixed in source; there is no alternate provider origin or hosted test mode.

`gmailConnections.status({tenantId})` is owner-only and returns connected/mailbox/generation/needsReconnect, never tokens. Authenticated Node actions are `gmail.beginConnect`, `completeConnect`, `listMessages`, `previewMessage`, `importMessage`, and `disconnect`. Lists contain at most 20 Inbox messages with sender/subject/date/snippet plus an explicit next-page token; bodies are fetched only for selected previews/imports. Every provider action verifies ownership before access and again before returning private data or committing an import. A generation guard rejects responses from a disconnected/replaced connection. Google authorization failures clear local encrypted credentials and set `needsReconnect`; disconnect clears local access first and reports whether provider revocation also succeeded.

The Next routes must authenticate the WorkOS session, enforce the fixed origin on connect POST, and validate a signed HttpOnly Secure SameSite=Lax callback cookie against the current actor/session/state. Both begin and complete additionally require `{payload,signature}`: HMAC-SHA256 over the exact UTF-8 JSON payload, with base64url signature and the separate route key. Payload fields are `{v:1,purpose,userId,sessionId,issuedAt,browserBinding}` plus `tenantId` for begin or `state` and lowercase hex SHA256 `codeHash` for complete. Proofs expire after 120 seconds (30 seconds permitted clock skew). Browser binding and state are random 32-byte lowercase hex values. These proofs stay server-side. The backend binds all command arguments and the verified JWT subject, and stores a hash of the signed session ID for callback equality; it does not trust a browser-supplied actor or tenant alone.

Pending state expires after 10 minutes. A transaction consumes it before the code exchange, clearing its encrypted PKCE verifier immediately; exchange failure never reopens replay. Each state schedules deletion of that exact row at expiry. Token encryption is AES-256-GCM with a fresh nonce and tenant/mailbox-bound authenticated context. Access tokens stay in action memory. Refresh-token ciphertext is internal-only and cleared on disconnect/authorization failure; connection generation and import provenance remain for safe retry behavior. Do not rotate the encryption key without an explicit re-encryption or reconnect plan. Safe UI errors include `INVALID_ROUTE_PROOF`, `INVALID_OAUTH_STATE`, `ALREADY_CONNECTED`, `CONNECTION_CHANGED`, `RECONNECT_REQUIRED`, `NO_PLAIN_TEXT`, `MESSAGE_TOO_LARGE`, and `GMAIL_UNAVAILABLE`; Google response bodies and token values are never propagated as errors.

Verification uses the existing isolated local Convex process and signed JWT clients, plus mock HTTP responses for provider parsing/error bounds and pure crypto tests. The integration runner writes an allowlisted transition adapter **only inside its temporary local copy** to exercise internal state transactions with those signed identities. It is absent from the deployable `convex` directory. Fixture imports/inspection explicitly use that local URL/admin-key env file; none target managed staging. No test calls Google. Real OAuth consent and a selected-message browser import are a separate human/provider acceptance gate after reviewed deployment.

Only `https://www.googleapis.com/auth/gmail.readonly` is requested. It is a restricted scope; a production rollout has separate Google verification/data-handling requirements. External Testing refresh tokens normally expire after seven days for this scope; the UI must offer reconnection rather than imply a permanent session.
